# DEMO-01 — Competition workflow completion audit

**Date:** 24 October 2026 (Asia/Jakarta). **Scope:** read-only requirements, source, checkpoint and runtime-status inspection. This report is the only DEMO-01 file. No feature was implemented. The planned full Checkpoint 2F application/database cutover is paused.

## 1. Executive summary

The existing application supports a credible core journey: role login; Relawan PFA, assessment and T0-Suspect; Healthcare reception, acknowledgement, verification, classification and explicit legacy Referral; and Admin aggregate views. The verification ledger records actual browser evidence for selected versions of that journey, including a genuine offline/reconnect path. This is **historical selected-scope evidence**, not a current end-to-end pass across the newly added Referral/Dispatch UI.

The major demo break is at the new independent clinical Referral and Dispatch path. Checkpoint 2D+2E added UI, read projections, events and synthetic fixtures, and reported guarded automated passes. The development database still has **23 applied migrations; both additive 2B migrations are Pending** on a read-only `docker compose exec -T app php artisan migrate:status --no-ansi` check during this audit. `HealthcareOperationsRead::ready()` therefore disables the new operations controls. The six Compose services were observed running, including Nginx (read-only `docker compose ps --format json`), so the earlier 2F-B2.2 report's Nginx-stopped state is no longer current. No HTTP page, socket delivery or browser flow was checked in DEMO-01.

Other important gaps are a true Admin density heatmap, live Admin aggregate updates, misleading `totalConfirmed` fallback semantics, QR scanning, complete adaptive non-verbal interaction, actual Background Sync API and automatic/encrypted SMS. The last two must not be claimed to judges. Workflow requirements for encryption, pseudonymization and E2EE are also unfulfilled or unverified; do not describe the prototype as production secure. The immediate sequence is a small Admin metric-truthfulness fix that does not depend on schema, then owner-approved additive deployment and fixture preparation, then focused browser regression before expanding lower-priority features.

**Counting rule:** 101 distinct capabilities below; one status per row. `IMPLEMENTED_AND_VERIFIED` means source plus *dated, scoped recorded* browser/runtime or automated evidence, not a new audit-time test or universal proof. `IMPLEMENTED_NOT_RUNTIME_VERIFIED` means source/automated coverage without direct relevant runtime/browser evidence. `BLOCKED` means implemented functionality cannot run on the observed development schema. `PARTIAL` means only part of the requirement is present. `NOT_IMPLEMENTED` means no current matching capability was found in inspected routes/source. `DESIGN_DECISION_REQUIRED` marks incompatible requirements or unsafe policy choices. `UNKNOWN` means the inspected evidence is insufficient to decide. Priority describes demo impact, not a waiver of the requirement.

Their historical browser evidence remains valid within its dated scope.

## 6. Requirements/design conflicts and decisions

1. **Q17 auto-T0 versus explicit confirmation:** WF 244–248 and 478–484 say automatic T0 status on Q17; the later T0 design §§10, 58 requires Q17 interruption, then human verification and final send. Current UI follows the later safety design and preserves manual answers; this prevents silent emergency transmission. Keep both texts visible as a conflict; owner approval is needed for any clinical-policy reinterpretation.
2. **T3 downgrade:** `RAPID_MIND_HEALTHCARE_WORKSPACE.md` and `RAPID_MIND_REFERRAL_RESPONSE_INTERACTION.md` final flow specify T1/T2 after secondary T0 verification, while `HealthcareController::classify` accepts T3. Existing code is not proof of an approved T3 policy. Resolve before demonstrating that branch.
3. **SMS:** WF requires automatic encrypted gateway fallback. `RAPID_MIND_T0_EMERGENCY_INTERACTION.md` §58 locks a user-mediated native composer; source uses `sms:119` with human send. The latter is operationally honest but does not fulfill automatic encrypted SMS. The exact production destination/payload/security need owner decision. The current plain-text composer payload must not be described as encrypted.
4. **Background sync:** WF requires Service Worker Background Sync and closed-app transmission. Current worker only caches/navigates; document `syncManager` handles reconnect/visible replay. The B3E browser test verified reconnection with a restored browser document, not closed-app Background Sync API.
5. **Admin patient master versus aggregate-only privacy:** WF 284–287 requests named/NIK patient master/sparkline in Admin; WF 611–613 and the later Admin design confine Admin to anonymous aggregate data. No Admin patient master exists. Preserve the privacy boundary until the owner explicitly resolves it.
6. **Alert presentation:** WF asks pulsing/flashing and loud alert; later T0/Healthcare visual direction bans continuous emergency animation and prefers finite cues. Source uses finite sound and static exceptional red. Any alert change requires usability/safety review; there is no measured `<1s` guarantee.
7. **JWT SSO terminology:** WF calls universal JWT SSO; current browser path uses Laravel session with JWT-capable API. “Single login with role routing” is a demonstrated prototype claim; external SSO is not.
8. **NIK as collision key:** WF 182 requests NIK-based unique identity, while later architecture permits unidentified cases and stable internal UUIDs. NIK cannot be universal primary key. Reconciliation policy needs an explicit design decision.
9. **Clinical analytics:** WF 63–69 suggests 30-day recovery/PTSD interpretation; source shows case counts only. Counts must not be presented as patient recovery, prevalence or diagnosis.
10. **Referral/Dispatch split:** WF 263–265 uses referral/transport language together; the later dedicated Referral/Response design makes clinical classification, Referral and Dispatch independent. Source 2C/2DE follows that refinement while legacy Referral movement remains for compatibility.
11. **PFA record versus guide-first interaction:** WF 175–176 asks for offline PFA recording, while WF 91–92 and the Relawan shell design present PFA as a human-centered, low-entry guide. The current UI implements the guide. A separate lightweight record needs a product decision; it must not turn the PFA encounter into a burdensome checklist.
